# Authorized Application Form Work

Follow the [required reading by task](application-answer-workflow.md#required-reading-by-task) before using this stage. Its reading requirements apply to both the writer and the independent reviewer. Apply it with the entrypoint's required context and punctuation guidance and the application prose profile. Keep working records private unless the user requests them. These are decisions tied to the actual application, not headings to paste into every answer. All examples in this reference are fictional.

## Coordinate writing and authorized form work

For a supplied document template, apply the [shared layout guidance](document-layout.md) to preserve the original form while entering verified values and checking the final deliverable.

This section does not grant permission to browse, enter personal data, upload, save, download, or submit. Apply it only when the user has authorized the relevant action and the necessary tools and destination are available. Otherwise provide the requested text or plan and identify what has not been performed. Follow the applicable form or file tool's instructions; do not imitate an unavailable action or claim success from a plan. Separate dissatisfaction with prose quality from explicit authorization to submit the identified version. Do not delay an authorized action for optional polishing or repeat an approval request already answered; report any mandatory blocker immediately. A later report that the user submitted changes the action state and prevents another submission.

When the user has authorized work on the overall application, start by surveying both required and optional fields and attachments, including conditional sections, while drafting and independent review are still in progress. For each optional item, check what the form accepts and whether the applicant has relevant, verified material. Separate material ready for review, useful material that still needs preparation, and items to leave blank because they do not fit or cannot be verified. Bring the usable material and any remaining decisions to the user early enough to review; a field being optional is not a reason to discover it at submission time. Do not invent entries, fill irrelevant fields, or spend the time reserved for a timely submission on optional material. Do not wait for prose approval to start those authorized checks, or let essay work postpone a missing required value until final entry. Keep unapproved prose distinct from approved text and perform only the form actions already authorized.

At the start of authorized form work, inspect the complete field list, required attachments, consents, and final confirmation steps rather than assuming the essay is the only remaining item. This inspection does not itself authorize a signature or submission. When authorized form entry is in progress and the form supports partial saving, save completed ordinary fields before a missing attachment or attachment troubleshooting consumes the remaining time. If the form requires attachments before saving, report that observed constraint rather than promising a partial save. Preserve the exact canonical answers and verified education details while entering them.

Keep prose approval, saved-field readback, whole-form validation, session availability, and submission receipt as separate states. Early enough to resolve missing items within the existing deadline reserve, use an authorized non-submitting review or validation flow across the whole form, including repeated history entries and conditional fields. Resolve missing required values through authorized records or necessary user questions early, then verify the entered result; merely labeling a required value unknown does not make the form ready. A successful draft save or a native `required` property of `false` does not establish that the site's full submission rules pass. If no non-submitting validation is available, report the remaining limit without postponing known missing items; do not use final submission or legal consent as a test without the required authority. Follow the confirmed status and supported instructions for ongoing entries; never invent an end date, mark ongoing work complete, or fill optional fields indiscriminately to clear validation. Escalate unresolved required values while time remains to resolve them.

Include whole-form checks and any needed reauthentication in the existing deadline reserve, without spending it on optional prose changes. At handoff, report known access or validation blockers with the canonical text and verified save state; an earlier save does not prove current access. Do not imply that an interruption extends the deadline or that late submission or supplementation is available without confirmed official permission for that application.

Distinguish choosing an address in a popup, changing a visible field, saving the whole application, and submitting it. An address selection or a popup closing is not evidence that the application was saved. For a save claim, retain the observed whole-application save result and, when authorized and supported, reopen the application and compare the persisted fields with the canonical version, including unchanged fields and attachment state. A success message without readback establishes only that the save was acknowledged; state any unavailable persistence check. Report failed, pending, and uncertain actions separately. Saving is not submission. Keep the actor separate from the observed state: seeing a completion screen does not establish that the assistant clicked submit. Give the user's direct completion report priority when reconciling concurrent actions, check an uncertain result before retrying, and do not repeat a completed submission.

If the user says they will submit personally, stop issuing form-changing or submission actions immediately and disclose any action already in flight whose outcome is uncertain. Do not wait for a completion report before yielding control, or treat the handoff itself as proof of submission. For a tool-observed submission claim, retain the site's receipt or submitted status tied to the identified application. A clicked button, sent request, or passed validation is not that evidence. Apply the existing uncertainty and retry checks to interrupted submissions; preserve the distinction between unattempted, rejected, uncertain, and confirmed states and the user's direct completion report.
