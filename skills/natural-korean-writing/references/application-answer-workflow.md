# Application Answer Workflow

Read this entire reference when drafting, revising, or reviewing application answers. Apply it with the entrypoint's required context and punctuation guidance and the application prose profile. Keep working records private unless the user requests them. These are decisions tied to the actual application, not headings to paste into every answer. All examples in this reference are fictional.

## Select experiences against the complete prompt

Recover each exact question and all accompanying guidance, required subquestions, length limits, and counting rules from the supplied application. Preserve their wording in the working record; a shortened title such as `지원동기` is not a substitute for the full prompt. Map each requested element to the evidence and answer passage that will address it before drafting. Do not silently turn employer guidance into an optional suggestion or invent unpublished selection criteria.

Keep that coverage map through the final review: for every required subquestion and explicit user correction, identify the exact sentence or connected passage in the current complete answer that addresses it. A polished answer, relevant anecdote, or reviewer assertion does not fill a missing requested element. For a strengths-and-weaknesses question, verify both in the actual text; do not pass a strengths-only answer because the overall personality story sounds convincing. Distinguish optional examples in employer guidance from mandatory requirements, but treat a user's explicit request to include a particular element as an active constraint. Recheck coverage after shortening, reordering, or style edits. If a required element lacks evidence, flag the specific gap instead of inventing it. If it is missing from locked text, seek or use explicit revision authority for that field without changing unrelated approved answers.

Compare plausible experiences against that map before choosing one. When several supported candidates exist, compare their coverage, the applicant's actual contribution, available evidence, and overlap with the other answers. A technically impressive experience can be a poor fit for the question. If only one supported candidate exists, assess its gaps without inventing a second experience. If a required element remains unsupported, retrieve available material or identify the missing fact; do not disguise the gap with a fluent sentence. Keep this comparison out of the submitted answer unless requested.

For a company-specific motive or plan, identify the official company material and current role posting that support the claim, along with their date and role scope. Use available authorized sources; if current evidence cannot be checked, qualify the claim or ask for the missing source. An old experienced-hire posting, a third-party summary, or a plausible technical inference does not establish the current entry-level role's stack or duties. Link the supported company characteristic to the applicant's own confirmed interest, experience, or decision: company praise and a separate personal anecdote do not by themselves explain why this person chose this company. Keep source links in the working evidence or requested review; include them in the submitted field only when that format calls for them.

Check personal records against the applicant's own evidence. For education, use the specific enrollment or completion record for that person and cohort. A current course page does not establish a past cohort's name, dates, hours, completion, or attendance. Never manufacture a cohort number or infer it from an adjacent program or calendar year.

For a motivation answer, start from the applicant's confirmed choices, experiences, and reasons, then connect them to the supported work or goal. A list of company duties followed by `제게 맞습니다` is not that connection. Preserve distinctions such as using different products for different purposes instead of compressing them into choosing one product. Personal convenience or preference is not proof of objective product superiority or other users' behavior. Do not invent employer defects or a market-wide conclusion from one person's account.

For a question asking for personality words or values, select labels that the actual behavior supports. Accepting and applying a correction may show openness to feedback; it does not alone establish listening skill. Reducing repetitive work can show efficiency; initiative additionally needs evidence that the applicant identified or started the action. If employer values matter, verify the official wording and select among the applicant's confirmed traits rather than inventing a personality to match a slogan. The connection is an interpretation supported by the example, not proof that the employer will endorse it. Start with the behavior and determine what it demonstrates; do not choose an attractive label first and force an unrelated episode to support it. A label such as accuracy needs an actual distinction, criterion, or checking action that explains what was made more reliable, not simply effort, completion, or the presence of a test. If the requested label is not supported, say so in the review or choose another supported trait when authorized rather than manufacturing evidence.

## Verify duty evidence in the actual answer

For an answer about job competence or contribution, extend the question-to-evidence map into a required review record. For each relevant main duty in the current official posting, connect these four items in order:

1. The exact official duty wording and its source, date, and role scope.
2. The applicant's own confirmed evidence: what the person actually handled, how, and any supported result. Separate team technology and others' work from personal use or implementation.
3. The exact corresponding sentence or connected passage in the final answer being reviewed. Record an absent passage as missing; a keyword match or a reviewer explanation does not fill it.
4. The strength and limits of that connection: a supported contribution the applicant can make directly, a transferable action with relevant similarities and differences, a task that still requires learning, or an unconfirmed connection. Mark missing source or personal evidence explicitly instead of treating it as demonstrated ability.

Build the record from the available official duties and personal evidence before drafting, then fill and verify the passage entries against the complete revised answer. Coverage means assessing the relevant duties, not claiming mastery of all of them or forcing every duty into the submitted field. For an entry-level applicant, retain a concrete contribution within the demonstrated scope, explain a transferable method only as far as the evidence supports it, and keep unfamiliar work as a specific learning need when the question calls for it. Participation in a team that used a technology does not establish personal proficiency in that technology, and related practice does not establish professional experience in the employer's systems.

Make this a pass condition for review: where the question asks for competence and personal evidence exists, the actual answer must show the action, its basis, and its connection to the relevant duty. Merely saying that an experience is related to the role, listing duty or technology names, or promising to learn is insufficient. If the evidence record supports a contribution but the final passage contains only relevance or aspirations, rewrite that passage and repeat the comparison. Do not pass it because the intended relationship appears in private notes. If the evidence itself is missing, narrow the claim, use another supported experience when authorized, or identify the missing material separately; never invent work, technical mastery, results, or responsibility to complete the map.

Keep this mapping and its labels in the working review record unless the user asks to inspect them. Write the supported relationship naturally in the application answer; do not paste the internal table, official-duty inventory, or pass/fail explanation into the submitted prose. After any revision that changes a mapped passage, recheck its personal attribution, evidence strength, and duty connection before treating that version as reviewed.

## Make the actor, object, and reason readable

When team size matters, make the total count unambiguous and keep the individual's role separate. In a fictional four-person project, `4인 팀으로` identifies the whole team more directly than a collaborator count that the reader might mistake for the total. Use only the confirmed total; never copy a sample team size into another applicant's account. A correct collaborator count can remain when it serves the requested meaning and no different phrasing was requested.

Mark each achievement's owner before turning notes into first-person prose. Distinguish the applicant, collaborators, the team, and unrelated people whose work the applicant observed or studied. A repository owner, a shared project name, or a merged pull request alone does not prove who implemented a feature. Where another person's achievement remains relevant, attribute it explicitly at the point of use and state the applicant's own action separately. Do not let a later `저는` or an omitted subject claim the other person's result.

Apply the same attribution check to AI-assisted work. When the source supplies them, show the problem the applicant identified, the criteria or decisions they made, what they changed with AI assistance, and what they actually checked or observed. Merely listing requests or prompts, such as `AI에 수정을 요청했습니다`, may leave the reader unable to assess the contribution. Explain the supported work without hiding material AI assistance or presenting AI-generated code or text as unaided manual work. A request alone does not establish a successful modification, and an AI suggestion is not a verified result. Preserve those limits when that is all the source establishes; do not invent diagnosis, criteria, implementation, review, or effects to complete a success story. State each contribution once where it supports the answer rather than repeating an explanation of the same criterion.

Do not open by listing experiences as a self-definition in the form `~을 경험한 ~입니다`. Replacing that wrapper with `경험을 가진` or `역량을 갖춘` does not explain the applicant's contribution. Start with the source-supported action, relevant role, or reason the question needs, without inventing a profession, expertise, or effect. Keep a meaningful self-introduction when it identifies the actual speaker or role, and retain valid uses of the noun `경험` when the experience itself matters. Preserve exact approved copy unless its revision is explicitly authorized.

An explicit user ban on an expression applies throughout the requested manuscript, not only to its introduction or an awkward use. If the user prohibits `경험한`, check the complete revised manuscript for that exact substring, including occurrences inside longer words and later paragraphs; a contextually plausible use is not an exception. A prohibition on that expression does not by itself prohibit the noun `경험`. Apply a later explicit instruction authorizing changes to previously locked occurrences within its stated scope, while preserving other protected copy. Check the underlying meaning after rewriting as well as the banned substring; neither a synonym that retains an empty self-definition nor deletion of a necessary fact is a solution. Quotations used to explain a rule or construct a test fixture are distinct from the manuscript being delivered.

At the first mention in every independently read answer, introduce an unfamiliar app's verified purpose and the applicant's role briefly. Preserve the actual action and object. In a fictional tool-care app, `공구별 손질 방법을 검색하는 앱` describes finding instructions; `공구를 찾는 앱` claims a different function. Do not infer a purpose from the name, and do not rely on a later answer or attachment to define it. Reuse the minimum introduction where needed without retelling the whole experience.

Connect technical detail to the supplied reason for a decision, the action taken, and its observed effect. Name the risk or constraint when it explains why the action mattered. A list of libraries, tests, or automation jobs cannot supply that relationship. Keep a technical name when it helps the reader assess the actual work; do not replace a supported action with vague praise or fill missing reasoning with an invented alternative. Preserve the distinction between a test's expected value, an executed test result, and an observed user outcome.

For repository-backed examples, compare the initial description with the relevant final code, review changes, and actual test records when accessible. Do not repeat an initial proposal as the final behavior or infer that a test passed from its presence in source. If an essential source is inaccessible, state the evidence limit separately or narrow the claim. Explain the user-visible problem, the applicant's judgment, and what was actually checked in terms the intended hiring reader can follow. Transfer a checking method to an unfamiliar domain without claiming production experience, loss prevention, or safety guarantees that the source does not establish.

Repair nominalized motivation sentences at the meaning level. Phrases such as `~한 일을 다른 곳에서도 하고 싶습니다`, a noun pile ending in `개발을 맡습니다`, or a long duty modifier ending in `지원한 이유입니다` can hide the actual reason or break clause relationships. Name the supported action with a fitting verb and state why the applicant chose it; do not merely swap the ending while retaining an empty connection. These are review signals, not universal bans on `일`, `맞다`, or `맡다`. Keep a clear supported assignment such as `행사 진행을 맡았습니다` when appropriate, and respect an explicit user's narrower expression ban and protected copy.

Remove stock closing sentences that merely repackage an already described action as `~하는 것이 목표입니다` or `~한 것입니다`. End with the actual action or necessary content instead of replacing the wrapper with a similar slogan. When the question asks for goals or plans, retain the specific intended outcome and supported plan; removing a formula must not remove that answer or turn an intention into completed work. Judge the sentence's contribution, not just its ending: a genuine explanation using `~한 것입니다` may clarify a needed meaning or scope. Preserve locked wording and apply any explicit wording restriction within its stated scope.

If the user explicitly excludes intention endings such as `~려 합니다` and `~려고 합니다`, check the complete requested manuscript for those patterns as well as other current expression bans. Preserve the actual action, supported contribution, interest, and any genuine future plan through a context-appropriate rewrite. Do not merely substitute another stock intention formula, remove all future meaning, or turn an intended action into a completed result. A ban on a verb and its inflections requires checking the inflected occurrences too; a dictionary-form search alone is insufficient.

When the user requests a calmer application voice with fewer pledge-like statements, apply that preference across the application, not only to service-design answers. State completed personal actions as facts. For work the applicant has not yet been assigned, express a grounded contribution they could make or a supported interest without promising decisions, authority, or outcomes they do not control. Keep the actual action and its connection to the official duty visible: softening the tone must not retreat from supported capability into only wanting to learn. Do not mechanically end every sentence with `생각합니다`, turn completed work into uncertainty, or remove all intention. Retain genuine personal plans and commitments established by the source and needed by the question. Reapply the duty-evidence passage check above to the softened answer, rather than treating a gentler ending as sufficient.

## Explain service operation through tone revisions

When an answer asks how a service works or should be designed, explain the actual or proposed operation: who does what, under which conditions, using which information, and what the service returns or changes. Repeated `~하겠습니다` promises do not supply that explanation. Keep planned functions identifiable as a proposal even when using descriptive present-tense sentences within it; do not make an unimplemented design sound live. Retain genuine personal commitments where the question or source calls for the applicant's future action, rather than replacing every future ending mechanically.

For a tone or ending revision, compare the original and revised complete passage for every feature, actor, condition, input, output, and actual or planned state. Keep the relationships between them as well as the nouns. Do not drop a filter, exception, permission condition, data item, or output merely to avoid a repeated ending or make the passage shorter. Combine clauses only when those distinctions remain readable, and do not add a feature, role, result, or benefit to improve the flow.

## Keep execution, learning, and intended contribution concrete

When a user flags vague wording such as `동작을 확인했습니다`, identify the supported subject, environment, and action before rewriting. If the source establishes that the applicant ran a particular feature on named platforms and tested it, state that action directly rather than replacing one vague checking phrase with another. Do not promote reading code, seeing a screenshot, requesting an AI change, or finding a test file into running the software. Do not invent cases, successful outcomes, coverage, or performance gains merely to make the sentence concrete. Apply an explicit user's wording restriction within its scope; the verb `확인하다` itself is not universally wrong.

For a learning example, make the starting point clear at the scope the evidence supports: first learning this language, tool, subject, or task is not necessarily first learning development or beginning a career. Preserve earlier relevant experience. When the user wants rapid learning emphasized, use a confirmed duration or concrete progression if available; an enrollment, award, or completed task alone does not establish speed. Explain how the learned knowledge was actually applied and, when supported, who benefited and how. An intention to help someone is not an observed benefit. Select and arrange evidence around the user's stated value rather than substituting a list of education or awards for that point. Do not invent a starting level, learning duration, application, or beneficiary to complete the narrative.

In an entry-level aspiration, distinguish a contribution within assigned responsibilities from authority to decide priorities, change a product, or commit a team. A personal interest in user feedback does not confer authority to implement every request. When supported by the role and the applicant's intention, describe carrying out assigned work accurately or promptly, communicating a concern, or proposing a change through the applicable process without inventing that process. Do not promise unilateral product changes, guaranteed speed, or broader business results. This does not prohibit initiative: preserve evidence of self-started improvement and legitimate proposals, and do not impose obedience as a universal cultural trait or assume an unpublished hierarchy.

## Apply a requested formal vocabulary

When the user requests a more formal application voice, carry that preference through subsequent editable drafts in the same scope instead of reverting to casual word choices. For example, an explicit preference for `수정하다` over `고치다` should cover applicable wording about revising text or software, including inflected forms. Check the word's actual object and action: do not mechanically use `수정하다` for repairing a physical object, treating an illness, or another meaning it does not express. Choose a fitting formal verb when the broader register preference applies. Preserve exact quotations, protected names, and unrelated approved fields unless their revision is explicitly authorized. Formality does not require noun stacks, inflated claims, or stiff predicate-object combinations. Treat the requested preference as scoped user guidance, not a universal rule that ordinary Korean verbs are wrong.

## Describe limitations without erasing them

When the question or user asks for a weakness, state the source-supported difficulty plainly enough to remain recognizable. Do not disguise it as an unqualified strength, omit its cost, or assert complete recovery merely because the applicant later gained useful insight. Separate the recurring limitation, its actual consequence, any confirmed coping action, and what the applicant learned about their own choices; use only the elements supported and requested. Greater self-understanding or better selection criteria do not prove consistent execution or that the weakness no longer occurs. Do not invent a productivity routine, outcome, diagnosis, or moral defect. Preserve the difference between the applicant's concern about how they might appear and an established character judgment. A measured formulation can avoid harsh self-condemnation without hiding the acknowledged weakness or weakening a genuine supported improvement.

## Complete the answer's point

Check the structure of each editable answer against its exact question: the central claim, the facts and actions supporting it, and the conclusion those facts justify must connect in the submitted text. This is a reasoning check, not a compulsory three-paragraph template or a demand for the same ending in every answer. A sequence of events can finish grammatically while leaving the reader to infer why it answers the question. Where needed, close with a concise, source-supported synthesis that directly completes that answer: why the choice follows, what the behavior shows, or what the requested plan addresses. Do not append a generic promise, repeat the trait word without explanation, or invent a lesson merely to create a conclusion. If the point is already complete, do not add a redundant summary.

A request to improve closure in one answer does not unlock another approved answer. Keep each unchanged approved field exact, apply the latest correction only within its authorized scope, and check the revised whole for lost evidence and duplicated conclusions. A review note explaining the intended conclusion does not repair its absence from the actual answer. In a motivation answer, compare the opening reason, the selected episode, and the closing point for the same supported line of reasoning. An example of careful checking does not by itself explain a stated interest in accessibility, and an example of convenience does not prove reliability. If both values are relevant, state their source-supported relationship in the answer; otherwise select a better-supported example or narrow the conclusion within the authorized scope. Do not invent user feedback, a causal link, or a new motive to make the parts appear unified. A smooth transition word alone cannot repair a change of subject.

## Read the whole company's answer set

Gather all available answers for the same company, including unchanged fields, before approving an individual revision. Read the complete set for repeated motives, repeated experience narratives, and repeated future aspirations, as well as contradictory facts or timelines. Give each answer a distinct role tied to its own full question. Different wording for the same story is still duplication. Reusing an experience can be justified when the question needs a different supported aspect; preserve the brief local introduction needed by a first reader. Do not invent a new experience just to create variety. If some answers are inaccessible, name that limit and do not claim the entire set was reviewed.

Treat the user's own edits and accepted sentences as the current baseline. A local correction permits changes within its stated scope; it is not permission to restore an older draft or polish every field. Compare the revised answer against that baseline for lost claims, altered facts, and changed protected characters. If the user explicitly requests ASCII single quotation marks (`'`, U+0027), apply that preference to editable text in the requested scope. It does not override separately locked wording, protected source quotations, or literals, and it is not a universal Korean punctuation rule. A request that explicitly changes a particular locked quotation applies to that quotation only.

Where the user also designates a service or app name for consistent quotation, check the requested scope by textual role before checking occurrences across the assembled answers. A request about names in body prose covers the designated later paragraphs and particle-attached mentions, not automatically a resume's standalone project titles, labels, or table values. If the requested resume format distinguishes a project name through its title structure, omit decorative name quotes there while retaining required body-name quotes, exact search strings, and actual quotations. Follow explicit title-format or protected-quotation instructions instead of declaring all title quotes wrong. Compare consistency within the same role rather than forcing identical punctuation on different roles. Where name quotation applies, keep the particle outside the quotes. Replace misplaced existing quote boundaries instead of adding another pair around the name; check for doubled, unmatched, or leftover marks in the complete phrase. Do not assume that introducing the name once satisfies a request covering later body mentions, and do not extend a one-phrase word choice to unrelated passages.

## Review and freeze the actual version

When independent review is requested or already established, use the independent-review procedure in SKILL.md. Give the reviewer the exact questions and guidance, the full same-company answer set, source evidence, latest corrections, locked text, and counting rules within the authorized disclosure scope. Tie findings to the exact version or fingerprint reviewed. Record actual findings for question fit, facts and attribution, duplication across the set, and natural Korean; a statement that the rules were read or a checkmark alone is not review evidence. For competence or contribution answers, require the duty-evidence record above and judge its corresponding passages in that exact version before passing the answer. Distinguish findings received and resolved from review still pending or unavailable. This application review is separate from the repository's benchmark protocol, whose reviewers receive only their prescribed evaluation inputs.

After accepted corrections, keep one canonical version containing the exact questions and guidance, complete answers, measured counts with their convention, and the review findings that apply to that text. Inspect the assembled answers, including unchanged passages. Do not describe a file as validated merely because its earlier draft passed review. Any later change creates a new version: compare its text with the prior version, recount the affected answers, and repeat the relevant checks and any required independent review. Keep an unresolved version distinct from the last validated version.

When the user asks to inspect answers in chat, deliver every full exact question, accompanying guidance, complete answer, and actual character count with the counting convention. Count the exact answer string after its last edit, using the destination's rule when known; state a counting limitation instead of guessing. Question text, headings, and review notes do not belong in the answer's count unless the destination counts them. Honor an explicit answer-only output request while doing these checks internally.

When the user has requested or established chat review before final file production, show the complete current version in chat and obtain approval of that version before producing the final deliverable. Approval of an earlier version, one sentence, or the direction of a revision does not approve a subsequently changed whole text. An authorized working draft may be saved for editing or review, but keep it distinct from the final file and do not claim that draft creation completes approval. If the current complete version is already approved and final file production is authorized, proceed without asking again. Outside this chat-before-final workflow, follow the existing authorization for file work without introducing an extra approval stage.

When saving a final file is authorized, compare its contents with the canonical text after writing, not merely its name or modification time. A plan for final file production must also include this readback comparison as a future step, including when the current complete text is already approved; do not report a planned check as completed. Freeze wording only after resolving material findings. Reserve time for the user's review and any authorized entry, attachments, saving, reopening, and submission. Base that reserve on the known deadline, available time, and actual remaining work rather than a universal number of minutes. Once the reserve is needed, stop optional comparisons and speculative rewrites; change only a material error or an explicit user request, and repeat the affected checks. Report unresolved limits instead of rushing an unreviewed new draft into use.

## Carry the approved text through authorized form work

This section does not grant permission to browse, enter personal data, upload, save, download, or submit. Apply it only when the user has authorized the relevant action and the necessary tools and destination are available. Otherwise provide the requested text or plan and identify what has not been performed. Follow the applicable form or file tool's instructions; do not imitate an unavailable action or claim success from a plan.

When authorized form entry is in progress and the form supports partial saving, save completed ordinary fields before a missing attachment or attachment troubleshooting consumes the remaining time. If the form requires attachments before saving, report that observed constraint rather than promising a partial save. Preserve the exact canonical answers and verified education details while entering them.

Distinguish choosing an address in a popup, changing a visible field, saving the whole application, and submitting it. An address selection or a popup closing is not evidence that the application was saved. For a save claim, retain the observed whole-application save result and, when authorized and supported, reopen the application and compare the persisted fields with the canonical version, including unchanged fields and attachment state. A success message without readback establishes only that the save was acknowledged; state any unavailable persistence check. Report failed, pending, and uncertain actions separately. Saving is not submission.

## Deliver requested originals and report download state

If the user requests a ZIP of submission-item originals, resolve the exact required item list and source files, preserve their original formats and contents, and package those originals. A newly written summary or conversion is not a substitute. Do not add unrelated working notes. Check the archive's entries and contents against the requested originals; identify missing source files instead of inventing replacements. A filename alone does not prove that the correct original was included.

Distinguish creating the archive, making it available, initiating a download, and confirming a file on the user's device. A browser may automatically save a download without showing a save dialog; inspect the actual download status and authorized local evidence rather than repeating a download just because no dialog appeared. A tool workspace path, an attachment link, or an opened preview does not establish that a file is on the user's PC. Report only the location and completion state that the available evidence supports.
