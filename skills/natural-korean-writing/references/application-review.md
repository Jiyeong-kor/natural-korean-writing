# Application Review and Version Freeze

Follow the [required reading by task](application-answer-workflow.md#required-reading-by-task) before using this stage. Its reading requirements apply to both the writer and the independent reviewer. Apply it with the entrypoint's required context and punctuation guidance and the application prose profile. Keep working records private unless the user requests them. These are decisions tied to the actual application, not headings to paste into every answer. All examples in this reference are fictional.

## Read the whole company's answer set

Gather all available answers for the same company, including unchanged fields, before approving an individual revision. Read the complete set for repeated motives, repeated experience narratives, and repeated future aspirations, as well as contradictory facts or timelines. Give each answer a distinct role tied to its own full question. Different wording for the same story is still duplication. Reusing an experience can be justified when the question needs a different supported aspect; preserve the brief local introduction needed by a first reader. Do not invent a new experience just to create variety. If some answers are inaccessible, name that limit and do not claim the entire set was reviewed.

Treat the user's own edits and accepted sentences as the current baseline. A local correction permits changes within its stated scope; it is not permission to restore an older draft or polish every field. Compare the revised answer against that baseline for lost claims, altered facts, and changed protected characters. If the user explicitly requests ASCII single quotation marks (`'`, U+0027), apply that preference to editable text in the requested scope. It does not override separately locked wording, protected source quotations, or literals, and it is not a universal Korean punctuation rule. A request that explicitly changes a particular locked quotation applies to that quotation only.

Where the user also designates a service or app name for consistent quotation, check the requested scope by textual role before checking occurrences across the assembled answers. A request about names in body prose covers the designated later paragraphs and particle-attached mentions, not automatically a resume's standalone project titles, labels, or table values. If the requested resume format distinguishes a project name through its title structure, omit decorative name quotes there while retaining required body-name quotes, exact search strings, and actual quotations. Follow explicit title-format or protected-quotation instructions instead of declaring all title quotes wrong. Compare consistency within the same role rather than forcing identical punctuation on different roles. Where name quotation applies, keep the particle outside the quotes. Replace misplaced existing quote boundaries instead of adding another pair around the name; check for doubled, unmatched, or leftover marks in the complete phrase. Do not assume that introducing the name once satisfies a request covering later body mentions, and do not extend a one-phrase word choice to unrelated passages.

## Review and freeze the actual version

When drafting or review is delegated, send the latest applicable user corrections and exact material version to each responsible worker, and identify the skill revision or fingerprint to read. Record the revision actually read with the returned findings. If instructions or materials change after handoff, update the affected workers and recheck their returned work before using it. Sending an update is not evidence that it was read or that a new review finished.

When independent review is requested or already established, use the independent-review procedure in SKILL.md. Give the reviewer the exact questions and guidance, the full same-company answer set, source evidence, latest corrections, locked text, and counting rules within the authorized disclosure scope. Include the source-coverage record and considered candidates so the reviewer can independently assess whether the selection follows the official requirements and each question, then test whether that reason is readable in the actual answer. These records are evidence to examine, not a verdict to endorse or a substitute for the reader-facing passage. Honor the actual review channel the user specifies; a different internal method is not interchangeable with a requested external thread. Record the actual reviewer or thread identifier, transmitted version, rules read, returned findings, their disposition, and unavailable evidence privately. Do not claim review completion before a substantive result returns. Tie findings to the exact version or fingerprint reviewed. Record actual findings for question fit, facts and attribution, duplication across the set, and natural Korean; a statement that the rules were read or a checkmark alone is not review evidence. For competence or contribution answers, require the [duty-evidence record](application-planning.md#verify-duty-evidence-in-the-actual-answer) and judge its corresponding passages in that exact version before passing the answer. Distinguish findings received and resolved from review still pending or unavailable. This application review is separate from the repository's benchmark protocol, whose reviewers receive only their prescribed evaluation inputs.

Keep factual support, paragraph relevance, and the readability of the relationship as separate judgments. For the answer's central claim and any material transition examined, a no-change finding must identify the connected passage and explain how it answers the concrete concern. Merely saying that every fact has a source, the opening states the direction, or the whole text was read does not settle that concern. A reviewer may conclude that no revision is needed, but must not supply a missing premise only in the review explanation. When the connection exists in the source but not the answer, request the authorized prose repair; when its source is missing, mark the evidence gap. If returned findings contain only factual confirmations or unsupported assurances of coherence, the coordinator asks the responsible reviewer for the missing passage-level assessment before treating content review as complete. Do not infer an internal cause, an unread rule, or deliberate noncompliance from a bad verdict alone.

After accepted corrections, keep one canonical version containing the exact questions and guidance, complete answers, measured counts with their convention, and the review findings that apply to that text. The designated reviewer inspects the assembled answers, including unchanged passages, against the exact questions, source facts, and latest constraints. Before delivery, the coordinator verifies the exact final version or fingerprint, substantive returned findings, disposition of material issues, and completion conditions. If the coordinator makes substantive changes or judges the content itself, it must first read the full references required for that role. Do not describe a file as validated merely because its earlier draft passed review. Any later change creates a new version: compare its text with the prior version, recount the affected answers, and repeat the relevant checks and any required independent review. Keep an unresolved version distinct from the last validated version.

When the user asks for a rewrite and the intended direction and essential facts are clear, deliver the actual revised text in the requested scope, not just an explanation of what will change. If a fact still blocks one part, give the supported revision and flag the specific gap outside it. If the user explicitly asks for options or reasoning before drafting, respect that stage instead. A delivered draft does not establish approval.

When the user asks to inspect complete application answers in chat, deliver each full exact question and accompanying guidance first, followed by its complete answer and actual character count with the counting convention. Immediately before sending, compare the assembled outgoing response with the canonical version for every requested question: a number-only heading such as `1번`, a shortened topic title, or a link to the form does not replace the question. Having kept the question in private notes or shown it in an earlier message does not satisfy this delivery check. If exact wording is unavailable, identify that gap rather than inventing or silently abbreviating the question. Count the exact answer string after its last edit, using the destination's rule when known; state a counting limitation instead of guessing. Question text, headings, and review notes do not belong in the answer's count unless the destination counts them. Honor an explicit answer-only output request while doing these checks internally. This format applies to complete application answers delivered for chat review, not every short reply or local sentence suggestion.

When the user has requested or established chat review before final file production, show the complete current version in chat and obtain approval of that version before producing the final deliverable. Approval of an earlier version, one sentence, or the direction of a revision does not approve a subsequently changed whole text. An authorized working draft may be saved for editing or review, but keep it distinct from the final file and do not claim that draft creation completes approval. If the current complete version is already approved and final file production is authorized, proceed without asking again. Outside this chat-before-final workflow, follow the existing authorization for file work without introducing an extra approval stage.

When saving a final file is authorized, compare its contents with the canonical text after writing, not merely its name or modification time. A plan for final file production must also include this readback comparison as a future step, including when the current complete text is already approved; do not report a planned check as completed. Freeze wording only after resolving material findings. Reserve time for the user's review and any authorized entry, attachments, saving, reopening, and submission. Base that reserve on the known deadline, available time, and actual remaining work rather than a universal number of minutes. Once the reserve is needed, stop optional comparisons and speculative rewrites; change only a material error or an explicit user request, and repeat the affected checks. Report unresolved limits instead of rushing an unreviewed new draft into use.
