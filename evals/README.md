# 평가 방법

평가는 정해진 문맥에서 의미와 사실을 보존하고, 독자에게 맞는 한국어를 작성하는지 확인합니다. 생성 결과는 서로 독립된 두 평가자가 판단하며, 판정이 다르면 세 번째 평가자가 추가로 평가합니다. Python 도구는 실행 기록과 집계의 일관성을 검사합니다. 한국어 품질을 자동으로 판정하는 도구는 아닙니다.

## 평가 자료

| 파일 | 평가 범위 | 사례 수 |
| --- | --- | --- |
| [core.json](core.json) | 의미, 문장 구조, 문맥과 결과 형식 | 24 |
| [approved-copy.json](approved-copy.json) | 확정한 문구의 보존 | 2 |
| [punctuation.json](punctuation.json) | 한국어 문장부호와 보호할 원문 | 7 |
| [context.json](context.json) | 후속 지시, 정보 경계와 문맥별 작성 조건 | 10 |
| [pragmatics.json](pragmatics.json) | 화자, 관계, 시점, 장소, 전달 방식과 발언 의도 | 7 |

다섯 파일의 50개 사례를 모두 실행합니다. 기술 지식을 추측할 필요가 없도록 각 사례에 필요한 사실을 제공합니다.

`core.json`의 분포는 다음과 같습니다.

| 분류 (`category`) | 평가 범위 | 사례 수 |
| --- | --- | --- |
| `meaning` | 의미와 사실 보존 | 4 |
| `grammar` | 조사와 서술어 호응 | 4 |
| `reference` | 생략과 지시 대상 | 3 |
| `register` | 말투와 높임 수준 | 3 |
| `artifact` | 글의 종류에 맞는 표현 | 4 |
| `literal` | 기술 원문의 정확한 보존 | 2 |
| `certainty` | 사실, 추론, 제안의 구분 | 2 |
| `delivery` | 바로 사용할 수 있는 결과 형식 | 2 |

`register`는 공손한 대화, 편한 대화, 호칭과 요청 방식의 일치를 각각 검사합니다. 편한 대화를 이유 없이 존댓말로 바꾸는 것도 실패입니다.

`approved-copy.json`의 `category` 값은 `approved-copy`입니다. 소개 문장을 보존하는지, 더 매끄럽게 고친다는 이유로 확정 문구를 바꾸지는 않는지 검사합니다. 두 사례 모두 `expected_exact`를 지정합니다.

`punctuation.json`의 `category` 값은 `punctuation`입니다. 영어 엔 대시와 엠 대시를 고치는 사례 2개, 가운뎃점, 붙임표, 한국어 줄표, 물결표의 쓰임을 확인하는 사례 각 1개, 코드와 경로, URL을 보존하는 사례 1개로 구성합니다.

`context.json`의 `category` 값은 `context`입니다. 다음 열 가지 조건을 각각 검사합니다.

1. 최종 문서에 불필요한 제작 이력을 노출하지 않습니다.
2. 나중에 명시한 수정 요청을 반영하고, 바꾸지 말라고 한 문구를 보존해 완성된 결과를 전달합니다.
3. 대화 말투와 원격에 게시할 초안의 존댓말을 구분합니다.
4. 짧은 대화에서도 실제 동작과 상태를 중립적인 동사로 설명합니다.
5. 사용자가 가운뎃점을 쓰지 말라고 한 문맥에서 그 제한을 지킵니다.
6. 문장부호 제한을 적용하면서 코드 원문은 정확히 보존합니다.
7. 확인된 수치라도 공개를 승인하지 않았고 독자에게 필요하지 않으면 제외합니다.
8. 제안서 전체에서 원래 어려움과 제안의 필요성이 실제 문장으로 연결되는지 확인합니다.
9. 이용 행동과 정성적 기대효과를 구분하고 측정하지 않은 효과를 단정하지 않습니다.
10. 익숙한 한글 이름, 정확한 기술 표기와 같은 대상의 고유명사를 구분해 사용합니다.

개인의 표기나 말투 선호는 해당 사례에 명시된 조건입니다. 모든 한국어에 적용되는 문법 규칙으로 일반화하지 않습니다. 공식 가운뎃점 용법을 요청하는 기존 사례와, 그 기호를 쓰지 말라고 요청하는 사례는 서로 다른 문맥을 검사합니다. `context.json`에는 출력 전체의 정답 문장을 지정하지 않으며, 보존하도록 명시한 문구와 기술 원문만 정확히 비교합니다.

`pragmatics.json`의 `category` 값은 `pragmatics`입니다. 같은 사실을 전달하더라도 누가 누구에게 언제 어디서 어떤 방식으로 말하는지, 무엇을 하려는 말인지에 맞게 표현하는지 검사합니다.

| 사례 식별자 | 비교하거나 확인할 조건 |
| --- | --- |
| `pragmatics-speaker-001` | 본인 명의 보고와 다른 사람의 진행 상황을 전달하는 보고 |
| `pragmatics-relationship-001` | 서로 반말을 쓰는 동료와 처음 연락하는 외부 담당자 |
| `pragmatics-time-001` | 바로 발송할 공지와 다음 날 예약 발송할 공지 |
| `pragmatics-place-001` | 같은 보관함을 보고 있는 대면 상황과 다른 건물에서 듣는 전화 상황 |
| `pragmatics-channel-001` | 담당자에게 보내는 비공개 인계와 이용자에게 게시할 공개 공지 |
| `pragmatics-intent-001` | 검토 요청과 작성 상태 보고 뒤 함께 검토하자는 제안 |
| `pragmatics-unknown-001` | 미확인 정보를 만들지 않으면서 필요한 부분만 확인하는 대응 |

앞의 여섯 사례는 각각 A와 B의 결과를 함께 작성합니다. 작업 사실과 상태는 유지하고 달라진 상황에 필요한 표현과 정보 범위를 평가합니다. 일곱 번째 사례는 알려지지 않은 수신자나 전달 방법을 추측하지 않고, 의미에 꼭 필요한 정보만 묻거나 사실을 더하지 않는 문장으로 작성하는지 확인합니다. 문맥 항목 전체를 질문하는 절차는 요구하지 않습니다.

일곱 사례 모두 `expected_exact`를 지정하지 않습니다. 사실과 관계를 정확히 전달하는 여러 자연스러운 표현을 허용합니다. 두 공지에 같은 절대 날짜를 쓰는 것처럼 양쪽에 적합한 표현이 같을 수도 있으며, 문장 모양이 다르다는 사실만으로 성공을 판정하지 않습니다. 각 결과가 해당 상황에 맞는지, 요청한 두 결과를 모두 작성했는지 실제 문장을 읽고 확인합니다. 상황별로 공개하지 말라고 한 정보는 해당 결과의 보존 조건에서 제외합니다.

## 사례 형식

각 JSON 파일에는 사례별 객체를 담은 배열을 둡니다. `expected_exact`를 제외한 필드는 모두 필요합니다.

| 필드 | 자료형 | 내용 |
| --- | --- | --- |
| `id` | 문자열 | 다섯 파일 전체에서 중복되지 않는 식별자 |
| `category` | 문자열 | 해당 사례의 평가 범주 |
| `context` | 문자열 | 독자, 글의 용도, 판단에 필요한 사실 |
| `instruction` | 문자열 | 생성용 에이전트가 따라야 할 요청 |
| `input` | 문자열 | 작성하거나 고칠 원문 |
| `expected_exact` | 문자열 | 출력 전체가 일치해야 할 때만 지정하는 기준 문구 |
| `must_preserve` | 문자열 배열 | 결과에서 반드시 전달할 의미와 사실 |
| `must_include` | 문자열 배열 | 결과에 반드시 포함할 내용 |
| `must_not_add` | 문자열 배열 | 근거 없는 상태 주장 등 추가하면 안 되는 내용 |
| `review_points` | 문자열 배열 | 실제 출력에서 확인할 의미, 관계와 표현 조건 |
| `critical_failures` | 문자열 배열 | 핵심 실패로 판단할 조건 |
| `applicable_rubric` | 문자열 배열 | 해당 사례에 적용할 평가 항목 |

표에 없는 필드는 허용하지 않습니다. `id`는 소문자와 숫자를 단일 붙임표로 연결한 형식으로 작성합니다. `applicable_rubric`에는 평가 항목을 하나 이상 중복 없이 지정합니다. 사례의 평가 조건과 기준 출력은 생성용 에이전트에게 전달하지 않습니다.

사례를 작성할 때는 결과에 담아야 할 내용과 잘못된 주장을 막기 위한 배경 조건을 구분합니다. `must_preserve`와 `must_include`에는 독자가 실제로 읽어야 할 내용을 적습니다. 아직 하지 않은 작업, 받지 않은 답장, 확인하지 않은 배포 결과처럼 거짓 상태 주장을 막는 조건은 `must_not_add`에 적고, `review_points`에서 해당 글의 목적에 맞게 확인합니다. 배경 사실이 제공됐다는 이유만으로 그 사실을 설명하는 별도 문장까지 요구하지 않습니다.

실행 절차에는 수행할 작업과 대상, 순서가 있어야 하고, 제안문에는 무엇을 제안하는지 드러나야 합니다. 이때 미착수나 미구현 상태를 따로 설명할 필요는 없지만, 이미 수행하거나 완료했다는 주장을 추가하면 실패입니다. 기대효과도 실제 이점을 설명하면서 제안과 전망의 범위를 지켜야 합니다. 거짓 주장이 없다는 이유만으로 필요한 의미가 빠진 결과를 통과시키지 않습니다.

상태 자체가 요청한 내용이면 출력에 남겨야 합니다. `register-neutral-actions-001`의 현재 상태와 다음 행동, `register-remote-draft-001`의 테스트 미실행 상태는 필수입니다. `certainty-cause-001`의 원인 불확실성, 제안의 필요성과 기대효과를 연결하는 실제 문장도 생략할 수 없습니다. 이 구분은 보호할 원문의 정확한 표기나 통과 기준을 완화하지 않습니다.

`meaning-close-001`과 `register-honorific-001`은 자유롭게 문장을 교정하는 사례이므로 `expected_exact`를 지정하지 않습니다. 교정 예문과 표현이 달라도 의미와 사실, 문법, 높임 등 해당 사례의 평가 항목을 모두 충족하면 통과합니다. 표현이 다르다는 이유만으로 보호할 원문을 훼손했다고 판정하지 않습니다. 확정 문구의 완전 일치와 코드, 경로 등 보호할 원문의 정확한 보존은 별도로 검사합니다.

## 평가 항목

| 평가 항목 식별자 | 판정 기준 |
| --- | --- |
| `meaning_preservation` | 의미와 사실 보존 |
| `no_unsupported_addition` | 근거 없는 내용 추가 방지 |
| `audience_fit` | 독자와 용도에 맞는 표현 |
| `natural_korean` | 자연스러운 한국어 문장 구조 |
| `register_consistency` | 말투와 높임 수준의 일관성 |
| `literal_preservation` | 보호할 원문의 정확한 보존 |
| `output_format` | 요청한 결과 형식 준수 |

평가자는 사례에 지정된 항목마다 `pass` 또는 `fail`을 판정합니다. 항목 평균으로 실패를 상쇄하지 않습니다.

제목, 본문, 표 등 문서 전체가 제공된 사례는 모든 영역을 문맥 속에서 읽습니다. 필요한 의미를 실제 출력의 문장이나 연결된 대목에서 확인하며, 키워드가 있다는 이유만으로 통과시키거나 평가자의 설명으로 빠진 의미를 보충하지 않습니다. 원문에 비공개 정보가 포함됐더라도 명시적으로 제외하도록 요청한 정보는 보존할 원문으로 취급하지 않습니다.

## 실행 설정

모든 역할에 같은 설정을 적용합니다.

| 항목 | 값 |
| --- | --- |
| `agent` | `codex` |
| `runtime_surface` | `codex-desktop` |
| `model` | `gpt-5.6-sol` |
| `reasoning_effort` | `high` |
| `sampling` | `runtime_default` |
| GitHub CLI | `2.97.0` |

| 역할 | 실행 조건 |
| --- | --- |
| 생성용 에이전트 (`generator`) | 사례마다 1회 |
| 평가자 A (`reviewer-a`) | 사례마다 1회 |
| 평가자 B (`reviewer-b`) | 평가자 A와 독립된 대화에서 사례마다 1회 |
| 추가 평가자 (`adjudicator`) | 두 평가자의 항목별 판정이나 핵심 실패 판정이 다를 때만 1회 |

각 사례, 역할, 시도는 모두 이전 기록이 없는 새 대화에서 실행합니다. 생성용 에이전트에게는 설치된 스킬과 `context`, `instruction`, `input`만 제공합니다. 평가자에게는 스킬이나 생성용 에이전트의 작업 기록을 주지 않습니다. 평가자 A와 B는 서로의 판정도 받지 않습니다.

`temperature` 등 직접 지정할 수 없는 샘플링 값을 추측하지 않습니다. 지정한 모델이나 추론 수준을 사용할 수 없으면 평가를 중단합니다. 다른 설정으로 평가하려면 결과 버전도 새로 정합니다. `runtime_version`은 실제 실행 환경에서 확인한 Codex Desktop 버전으로 기록합니다.

## 평가 준비

저장소 루트에서 실행합니다. 모든 텍스트는 BOM 없는 UTF-8로 읽고 쓰며, Python 명령에는 처음부터 `-X utf8`을 지정합니다.

```powershell
python -X utf8 scripts/validate_repo.py --print-digest
python -X utf8 scripts/run_evals.py prepare --version v0.1.0 --work-dir .eval-work
```

`prepare`는 각 사례의 생성용 프롬프트, 평가자 A와 B용 프롬프트, `.eval-work/run.json`을 만듭니다. 모델을 실행하지는 않습니다. `run.json`에는 다음 값을 기록합니다.

| 필드 | 내용 |
| --- | --- |
| `version` | 평가 결과 버전 |
| `tested_at` | 평가 묶음을 시작한 UTC 시각을 ISO 8601 형식으로 기록합니다. |
| `tested_skill_digest` | 평가 대상 파일로 계산한 SHA256 |
| `evaluation_identity` | 평가 내용의 동일성을 확인하는 SHA256입니다. 새 형식의 실행 기록에 포함합니다. |
| `operations_version` | 요청 전달과 오류 복구 등 운영 절차의 버전입니다. 새 형식의 실행 기록에 포함합니다. |
| `source_protocol` | 새 형식에서 평가 시작 당시의 평가 문서 원문을 보존합니다. 원래 해시를 다시 계산할 때 사용합니다. |

작업 폴더가 이미 있으면 `prepare`는 실행을 거부하며, 기존 `run.json`을 덮어쓰지 않습니다. 새로 평가할 때는 이전 기록을 보존하고 아직 없는 별도의 작업 폴더를 지정합니다. 평가에 영향을 주는 입력이 달라지면 기존 출력과 새 입력의 결과를 섞지 않습니다. 운영 문서나 전달 및 복구 절차만 바뀐 경우에는 아래 동일성 검사를 거쳐 완료 결과를 재사용합니다. 원래 해시와 평가 시각은 현재 값으로 바꾸지 않습니다.

생성용 프롬프트는 `.eval-work/prompts/generator/{id}.txt`에, 평가용 프롬프트는 `.eval-work/prompts/reviewer-a/{id}.txt`와 `.eval-work/prompts/reviewer-b/{id}.txt`에 저장합니다. 평가용 프롬프트에는 사례의 평가 조건을 넣고 실제 출력 자리에는 `{output}`만 남깁니다.

실제 평가 요청은 `scripts/run_evals.py`의 `render_reviewer_prompt(case, output)`으로 생성합니다. `output`에는 생성 결과의 원문을 그대로 전달합니다. 준비한 프롬프트 파일은 수정하지 않습니다. `aggregate`가 준비 당시의 프롬프트와 일치하는지 검사하기 때문입니다. `{output}`이 남은 프롬프트를 그대로 평가자에게 전달하지 않습니다.

```text
$natural-korean-writing을 사용하세요.

문맥:
{context}

요청:
{instruction}

원문:
{input}

요청한 결과만 출력하세요.
```

### 평가용 프롬프트

```text
다음 출력이 case의 요구 조건을 충족하는지 평가하세요.

보존 조건과 필수 포함 조건은 별도의 정확 표기 지시가 없으면 의미와 사실을 기준으로 판정하세요. 조건을 설명한 문장을 출력의 고정 문구로 취급하지 마세요.

literal_preservation은 코드, 경로, URL, 기술 식별자와 그대로 유지하라고 명시한 문구의 정확한 보존을 판정합니다. 보호 대상 밖에서 의미가 같은 표현이나 조사, 어순이 달라진 것만으로 이 항목을 fail로 판정하지 마세요.

완전 일치 기준이 null이 아니면 출력 전체의 문자, 공백과 문장부호가 그 값과 일치해야 합니다. null이어도 보호할 개별 원문은 정확히 유지해야 합니다.

Case ID: {id}
문맥: {context}
요청: {instruction}
원문: {input}
보존 조건: {must_preserve}
필수 포함 조건: {must_include}
추가 금지 조건: {must_not_add}
검토 기준: {review_points}
핵심 실패 조건: {critical_failures}
완전 일치 기준: {expected_exact_if_present}
적용할 rubric: {applicable_rubric}

실제 출력:
{output}

적용할 rubric 항목마다 pass 또는 fail을 판정하세요. 핵심 실패 여부와 근거를 함께 기록하세요. 문장을 다시 작성하지 마세요.
다음 JSON object 하나만 출력하세요.
{"id":"{id}","rubric":{"rubric_name":"pass_or_fail"},"critical_failure":false,"reason":"판정 근거"}
```

평가 결과 JSON에는 `id`, `rubric`, `critical_failure`, `reason`만 둡니다. `id`는 평가한 사례와 같아야 합니다. `rubric`에는 `applicable_rubric`의 항목을 빠짐없이 한 번씩 넣어야 하며, 값은 `pass` 또는 `fail`만 허용합니다. `critical_failure`는 불리언 값이고, `reason`에는 판정 근거를 적습니다. 알 수 없는 필드나 빠진 항목, 중복된 키, 다른 사례의 식별자가 있으면 집계하지 않습니다.

## 실행과 원문 저장

1. 생성용 에이전트를 새 대화에서 실행하고 실제 출력을 수정 없이 저장합니다.
2. `render_reviewer_prompt(case, output)`으로 실제 요청을 만들어 평가자 A와 B를 각각 새 대화에서 실행합니다.
3. 두 평가자의 항목별 판정이나 `critical_failure`가 다르면 추가 평가자를 새 대화에서 실행합니다. 같은 사례와 실제 출력, 두 평가자의 JSON을 전달합니다. 추가 평가자는 평가용 프롬프트와 같은 JSON 형식으로 독립 판정합니다. `reason`의 문구만 다른 경우에는 추가 평가자를 실행하지 않습니다.
4. 모든 실행의 설정과 시도 기록을 저장한 뒤 집계합니다.

| 파일 | 내용 |
| --- | --- |
| `.eval-work/generator/{id}.txt` | 생성용 에이전트의 실제 출력 |
| `.eval-work/reviewer-a/{id}.json` | 평가자 A의 JSON 원문 |
| `.eval-work/reviewer-b/{id}.json` | 평가자 B의 JSON 원문 |
| `.eval-work/adjudicator/{id}.json` | 판정이 다를 때 실행한 추가 평가자의 JSON 원문 |
| `.eval-work/execution.jsonl` | 사례와 역할별 실행 기록 |

`.eval-work/`는 Git 추적에서 제외합니다. 준비한 프롬프트와 중간 판정 파일, 임시 실행 기록은 커밋하지 않습니다.

### 파일로 요청 전달

완성된 요청을 직접 전달하는 대신 파일로 전달할 수 있습니다. 요청 내용과 역할별 실행 조건은 같습니다.

1. 생성용 파일에는 설치된 `SKILL.md`의 경로 안내와 `render_generator_prompt`가 만든 본문을 함께 저장합니다. 평가용 파일에는 `render_reviewer_prompt`가 만든 본문을, 추가 평가용 파일에는 `render_adjudicator_prompt`가 만든 본문을 저장합니다. 모두 BOM 없는 UTF-8을 사용합니다. 평가용 요청에는 실제 생성 결과를 넣고, 추가 평가용 요청에는 두 판정도 넣습니다. 준비 단계에서 `{output}`을 남긴 평가용 파일은 그대로 전달하지 않습니다.
2. 전달 전에는 파일 바이트를 해당 역할의 완성된 요청 전체와 비교하고 SHA256을 기록합니다. 생성용 파일의 비교와 해시에는 설치 경로 안내도 포함합니다. 파일 경로, 해시, 전달 지시와 실행 UUID를 비공개 작업 기록으로 연결합니다. 결과를 수집할 때도 파일이 바뀌지 않았는지 확인합니다.
3. 새 에이전트에게는 지정한 파일 전체를 UTF-8로 읽고 그대로 수행하라는 짧은 지시만 전달합니다. 요청을 다시 복사하거나 요약하지 않으며, 추가 판정 기준을 붙이지 않습니다. 생성용 에이전트는 설치된 스킬과 자기 요청만 읽습니다. 평가자는 자기 요청만 읽으며, 평가자 A와 B는 서로의 판정을 받지 않습니다. 추가 평가자에게만 두 판정을 제공합니다.
4. 모델, 추론 수준, 독립된 대화와 실행 횟수는 그대로 유지합니다. 공개 결과의 `prompt_sha256`은 `render_generator_prompt`가 만든 본문의 원문 바이트만으로 계산합니다. 설치 경로 안내와 파일을 읽으라는 지시문은 이 해시에 포함하지 않습니다.

실제 요청이 해당 역할의 완성된 요청과 다르거나 일부가 누락됐으면 요청, 파일, 오류와 생긴 출력을 보존하고 정상 평가로 집계하지 않습니다. 전달 오류는 연결 오류와 구분합니다. 에이전트 생성과 실제 전달 내용, 중단 상태, 전체 이력을 확인해 출력이 없다는 근거를 확보한 경우에만 해당 역할을 새 UUID로 한 번 복구할 수 있습니다. 수정한 요청이 원래의 완성된 요청과 일치하고 모델과 설정, 연결된 생성 결과와 판정이 그대로인지 먼저 검사합니다. 이미 완료한 다른 역할은 통과 여부와 관계없이 보존하며 다시 실행하지 않습니다.

출력이 있거나 이력이 잘렸거나 실행 결과를 확인할 수 없다면 출력 없는 오류로 처리하지 않습니다. 이미 출력이 생성된 실행의 품질이나 JSON 형식 문제도 재시도 사유가 아닙니다. 오류의 영향 범위를 확인할 수 없으면 관련 결과의 재사용을 중단하고 보존한 입력과 실제 전달 기록부터 대조합니다.

### 실행 기록

`execution.jsonl`은 사례와 역할의 조합마다 JSON 객체 한 줄을 기록합니다. 각 객체에는 `id`, `role`, `agent`, `model`, `reasoning_effort`, `sampling`, `attempt_log`가 필요합니다. `role`은 `generator`, `reviewer-a`, `reviewer-b`, `adjudicator` 중 하나입니다.

`attempt_log`의 각 항목은 다음 필드를 가집니다.

| 필드 | 내용 |
| --- | --- |
| `attempt` | 첫 시도는 `1`, 허용된 재시도는 `2` |
| `context_id` | 에이전트를 만들기 직전에 생성해 요청과 응답 파일에 연결한 UUID |
| `runtime_surface` | `codex-desktop` |
| `runtime_version` | 해당 시도의 실제 Codex Desktop 버전 |
| `status` | 완료는 `completed`, 출력 없는 오류는 `delivery_error`, `runtime_error` 또는 기존 기록의 `transport_error`로 구분합니다. |
| `retry_reason` | 완료된 시도는 `null`, 실패한 시도는 확인한 오류 종류 |

에이전트를 만들기 직전에 `scripts/run_evals.py`의 `new_context_id()`로 UUID를 생성합니다. 서로 다른 사례, 역할, 시도는 같은 `context_id`를 사용할 수 없습니다. Codex 내부 작업이나 대화의 ID를 공개 결과의 식별자로 쓰지 않습니다. 설정값은 에이전트 생성 요청에서, 실행 정보는 실제 실행 환경의 결과에서 가져옵니다.

### 재시도 조건

에이전트가 생성된 뒤 출력 없이 끝난 실행은 원인이 확인된 경우에만 같은 설정의 새 대화에서 한 번 복구할 수 있습니다. 잘못된 요청 전달은 `delivery_error`, 실행 환경의 오류는 `runtime_error`로 기록합니다. 이전 절차에서 사용한 `transport_error` 기록은 원문 그대로 보존하며 새 전달 오류를 이 상태로 기록하지 않습니다. 두 번째 시도는 실제 응답을 받은 뒤 `completed`로 수집합니다. 두 번째 시도도 실패하면 해당 역할의 복구를 중단하며 세 번째 모델 실행은 허용하지 않습니다.

복구 기록에는 원래 요청과 실제 호출, 오류, 생성된 에이전트와 중단 상태, 출력 유무를 확인한 전체 이력, 새 UUID를 연결합니다. 근거 파일과 원래 요청의 해시를 저장하고 수집할 때 다시 대조합니다. 새 요청에는 원래 프롬프트와 설정을 사용합니다. 생성 결과가 바뀌면 그 결과를 평가한 판정을 재사용하지 않으며, 추가 평가도 원래 생성 결과와 두 판정이 같은지 확인합니다.

에이전트 생성 도구가 생성 전에 요청을 거절했다고 명시한 경우에는 모델 실행이 시작되지 않았으므로 `attempt_log`에 넣지 않습니다. 최초 요청과 UUID, 오류 원문, 관찰 시각, 실행 환경의 버전, 에이전트가 생성되지 않았고 출력도 없다는 근거를 `.eval-work/dispatch-errors/`에 보존합니다. 생성 여부가 불분명한 시간 초과나 연결 끊김에는 이 예외를 적용하지 않습니다.

생성 제한이 발생하면 추가 평가 요청을 멈춥니다. 제한이 해소됐다는 근거를 확인한 뒤 새 UUID로 요청하며, 필요할 때만 별도 최소 진단을 사용합니다. 이름 충돌처럼 생성 전에 거절된 오류는 기존 에이전트의 결과를 새 응답으로 사용하지 않습니다. 이전 요청과 오류 기록은 유지하며 진단은 평가 결과에 포함하지 않습니다. 새 복구 정책은 생성 전 거절도 역할당 한 번만 복구하도록 제한합니다. 기록에 예정된 완료 상태가 있더라도 실제 응답을 받기 전에는 실행 결과로 수집하지 않습니다.

출력이 생성됐다면 품질이 낮거나 JSON 형식이 잘못됐다는 이유로 다시 실행하지 않습니다. 여러 출력 중 더 좋은 결과를 고르거나, 평가자의 판정을 직접 수정하지 않습니다. 필요한 추가 평가 결과가 없거나 형식이 틀리면 해당 사례를 통과시킬 수 없으며 릴리스도 만들지 않습니다.

## 판정과 릴리스 조건

평가자 A와 B가 일치하면 그 판정을 사용합니다. 추가 평가가 필요했던 사례는 세 판정에서 항목별 다수결을 구합니다. `critical_failure`는 세 판정 중 둘 이상이 `true`일 때 최종 `true`입니다.

`case_pass`는 최종 평가의 모든 항목이 `pass`이고 최종 `critical_failure`가 `false`일 때만 `true`입니다. `expected_exact`는 이 계산과 별도로 출력 전체를 비교합니다. 공백이나 문장부호를 제거하거나 유니코드를 정규화한 뒤 비교하지 않습니다. `expected_exact`가 있는 사례는 하나라도 불일치하면 항목별 판정과 관계없이 릴리스 조건을 충족하지 못합니다.

릴리스는 다음 조건을 모두 충족해야 합니다.

1. 의미와 사실, 보호할 원문, 확정 문구, 높임 수준 관련 핵심 실패가 없습니다.
2. `core.json`의 24개 사례 중 22개 이상 통과합니다.
3. `approved-copy.json`의 2개 사례를 모두 통과합니다.
4. `punctuation.json`의 7개 사례를 모두 통과합니다.
5. `context.json`의 10개 사례를 모두 통과합니다.
6. `pragmatics.json`의 7개 사례를 모두 통과합니다.
7. `expected_exact`가 지정된 모든 출력이 기준 문구와 완전히 일치합니다.

확정한 소개 문장의 보존, 공손한 대화의 높임 수준, 영어 `close`의 기계적인 직역 방지는 필수 회귀 사례입니다. 셋 중 하나라도 실패하면 릴리스를 만들지 않습니다.

```powershell
python -X utf8 scripts/run_evals.py verify-tracked --version v0.1.0
```

`aggregate`는 사례 식별자, 파일 수, JSON 형식, 평가 항목 식별자, 실행 설정, UUID 중복, 재시도 조건을 검사한 뒤 [runs/v0.1.0.jsonl](runs/v0.1.0.jsonl)과 [results-v0.1.0.md](results-v0.1.0.md)를 생성합니다.

같은 버전의 기존 결과와 바이트가 다르면 덮어쓰기를 거부합니다. 아직 공개하지 않은 버전을 다시 평가할 때는 이전 `.eval-work/`와 결과 파일 두 개를 저장소 밖의 작업 기록으로 보존한 뒤 새 결과를 생성합니다. 실패한 결과를 누락하거나 더 좋은 결과만 선택하지 않습니다. 이미 공개한 태그의 결과는 바꾸지 않고 새 버전으로 평가합니다.

`check`는 임시 입력에서 결과를 다시 계산해 추적할 두 파일과 바이트 단위로 비교합니다. `verify-tracked`는 임시 파일 없이 추적된 JSONL의 형식, 프롬프트의 SHA256, 실행 기록, 다수결 판정과 결과 요약을 다시 검사합니다.

두 명령은 실패한 평가 결과도 기록과 집계가 올바르면 통과할 수 있습니다. 실행 기록 검증의 성공을 릴리스 조건의 충족으로 해석하지 않습니다. 릴리스 조건은 `scripts/validate_repo.py`의 `--phase final`에서 검사하며, `--gh-path`에는 GitHub CLI 2.97.0 실행 파일의 절대 경로를 지정합니다.

실패한 사례를 빼고 집계하지 않습니다. 동일한 평가 내용에서 얻은 최초의 유효한 완료 결과는 성공과 실패 모두 재사용합니다. 운영 문서나 전달 및 복구 절차만 수정했다면 도구 회귀 테스트와 기존 원문의 재집계로 검증하며 50개 모델 평가를 다시 실행하지 않습니다.

스킬 실행 파일, 사례, 실제 프롬프트, 판정 기준이나 실행 설정이 바뀌면 관련 결과를 재사용하지 않습니다. 새 전체 평가 결과가 필요한 경우에는 이전 입력과 결과를 보존하고 별도 폴더에서 평가합니다. 서로 다른 평가 내용의 결과를 합치거나 일부 사례만 실행한 결과를 전체 평가 결과로 보고하지 않습니다.

새 릴리스를 만들지 않는 지침 수정에서는 현재 후보의 구조, 공개 파일, 패키지와 도구 테스트를 검사하고 변경 영향을 받는 사례의 실제 출력을 확인합니다. 기존 결과는 해당 버전의 기록으로만 유지합니다. 사용한 도구, 확인한 사례와 판정, 아직 검증하지 않은 범위를 별도로 기록하며 기존 해시나 판정을 고치지 않습니다.

`v0.1.0`의 과거 기록은 별도로 체크아웃한 원본에서 검사합니다. [기여 안내](../CONTRIBUTING.md#로컬-검증)에 따라 원본 경로를 준비한 뒤 다음 명령을 실행합니다.

```text
python -X utf8 scripts/run_evals.py --root ../natural-korean-writing-v0.1.0 verify-tracked --version v0.1.0
```

CI의 원본 대상 `final`은 과거 릴리스 기준을 검사할 뿐, 수정한 현재 후보의 품질을 판정하지 않습니다. 현재 후보에는 `build`, `pre-eval`, 단위 테스트와 패키지 검증을 적용합니다. 공개 평가 기록 세 파일은 원본과 바이트 단위로 비교하며, 현재 파일을 과거 평가 해시와 비교하는 기존 검사는 완화하지 않습니다.

### 추적할 JSONL

각 줄에는 다음 필드를 기록합니다.

| 필드 | 내용 |
| --- | --- |
| `id` | 사례 식별자 |
| `prompt_sha256` | 생성용 프롬프트의 BOM 없는 UTF-8 원문 바이트로 계산한 SHA256 |
| `output` | 수정하지 않은 생성 결과 |
| `generator` | 생성용 에이전트의 역할과 실행 정보 |
| `reviewers` | 평가자 A와 B의 실행 정보, 항목별 판정, 핵심 실패 여부, 근거 |
| `adjudicator` | 추가 판정이 없으면 `null`, 실행했다면 실행 정보와 판정 |
| `final_rubric` | 두 평가자의 일치 판정 또는 세 판정의 항목별 다수결 |
| `case_pass` | 최종 항목별 판정과 핵심 실패 여부로 계산한 통과 여부 |
| `critical_failure` | 최종 핵심 실패 여부 |
| `tested_at` | `run.json`에 기록한 평가 시작 시각 |
| `tested_skill_digest` | `run.json`에 기록한 평가 대상 SHA256 |
| `evaluation_identity` | 새 형식의 평가 내용 동일성 SHA256입니다. |
| `operations_version` | 새 형식의 운영 절차 버전입니다. |
| `dependency_sha256` | 새 형식에서 생성 결과와 평가 요청, 원래 판정의 연결을 확인하는 해시입니다. 이전 형식의 결과에는 추가하지 않습니다. |

각 역할의 실행 기록에는 `agent`, `model`, `reasoning_effort`, `sampling`, `attempt_log`를 보존합니다. 평가자와 추가 평가자에는 원래 판정의 `rubric`, `critical_failure`, `reason`도 보존합니다. 실행하지 않은 추가 평가자의 기록을 만들지 않습니다.

### 결과 요약

결과 문서에는 실제 평가 날짜와 대상 해시, 역할별 설정, 실행 횟수와 재시도 횟수, Codex Desktop과 GitHub CLI 버전을 적습니다. 사례 수, 통과 수와 실패 수, 평가자 간 불일치 수, 추가 평가 횟수, 핵심 실패 수를 집계하고 한계와 재현 명령을 함께 기록합니다. 실행 전에는 날짜, 실행 환경의 버전, 통과 결과를 미리 채우지 않습니다.

## 평가 대상 해시

`tested_skill_digest`는 평가를 시작할 때 다음 파일의 원문 바이트로 계산한 출처 기록입니다. 운영 문서가 바뀐 뒤에도 기존 결과의 이 값은 변경하지 않습니다.

1. `skills/natural-korean-writing` 아래의 모든 파일
2. `evals/README.md`
3. `evals/core.json`
4. `evals/approved-copy.json`
5. `evals/punctuation.json`
6. `evals/context.json`
7. `evals/pragmatics.json`

저장소 루트 기준 상대 경로의 구분자를 `/`로 통일하고 UTF-8 바이트 순서로 정렬합니다. 파일마다 다음 순서로 바이트를 SHA256에 넣습니다.

```text
상대 경로의 UTF-8 bytes
null byte 1개
파일 크기의 ASCII 십진수 bytes
null byte 1개
파일 원문 bytes
null byte 1개
```

파일 크기는 바이트 수입니다. 원문의 줄바꿈이나 유니코드를 정규화하지 않습니다. `evals/runs/`와 결과 요약 문서는 해시 계산에서 제외하며, 최종 커밋 SHA도 추적할 평가 결과 안에 넣지 않습니다.

평가 결과의 재사용 여부는 원문 해시와 별도의 평가 동일성 정보로 확인합니다. 스킬 실행 파일, 사례, 실제 생성 및 평가 프롬프트, 루브릭, 다수결과 배포 기준, 모델과 추론 설정, 독립된 대화 조건을 비교합니다. 이 문서의 ‘평가 자료’, ‘사례 형식’, ‘평가 항목’, ‘실행 설정’, ‘판정과 릴리스 조건’은 평가 내용에 포함합니다. 나머지 절은 운영 절차를 설명하며 새 판정 조건을 추가하는 용도로 사용하지 않습니다. 평가 기준을 바꾸려면 해당 기준과 실제 코드, 동일성 정보도 함께 갱신해야 합니다.

운영 문서나 복구 구현의 버전은 평가 내용과 분리합니다. 이전 형식의 결과를 사용할 때는 보존한 입력과 원래 프롬프트, 설정 및 판정 기준으로 동일성을 확인한 호환성 근거를 함께 보관합니다. 해시 두 개가 대응한다는 선언만으로는 재사용하지 않습니다. 현재 파일과 보존한 원문을 대조해 원래 해시를 검증하고, 완료된 출력과 판정의 연결도 검사합니다. 알 수 없는 문서 구조나 누락된 근거는 재사용을 허용하는 사유가 아닙니다.

`v0.1.0`의 이전 형식 결과는 [호환성 기록](compatibility-v0.1.0.json)으로 검증합니다. 원래 평가 문서와 코드의 의미 비교 정보, 실제 요청의 해시와 원래 결과 JSONL의 해시를 포함합니다. 이 기록은 출력이나 판정을 새로 만든 결과가 아니며, 비공개 작업 폴더 없이도 추적된 결과의 동일성을 검사하기 위한 근거입니다. 저장된 기록의 일치 검사는 외부 실행 시스템이 실제 호출을 보증한다는 뜻은 아닙니다.

새 형식의 결과에는 `evals/runs/{version}.inputs.json`으로 원래 평가 문서와 실행 메타데이터를 함께 보관합니다. `verify-tracked`는 이를 결과의 메타데이터와 대조하고 보존한 문서, 현재의 동일한 runtime과 사례로 원래 해시를 다시 계산합니다. 문서 원문은 JSONL의 각 사례에 반복해서 넣지 않습니다.

## 검증 범위와 한계

평가 자료 일부는 [교정 예시](../examples/before-after.md)와 겹칩니다. 이미 알려진 문제의 재발을 확인하는 제한된 회귀 평가이며, 처음 보는 한국어 전반의 품질을 측정하는 독립적인 성능 평가가 아닙니다.

두 평가자와 추가 평가자가 같은 모델을 사용하므로 판단의 편향을 공유할 수 있습니다. 문장 품질 판정에는 주관성이 남습니다. 한 번의 실행 결과를 다른 모델이나 모든 한국어 문서의 품질로 일반화하지 않습니다.

도구 테스트는 Python 표준 라이브러리로 실행합니다. 먼저 [기여 안내](../CONTRIBUTING.md#로컬-검증)에 따라 `v0.1.0` 원본과 `NKW_RELEASE_ROOT`를 준비합니다.

```powershell
python -X utf8 -m unittest discover -s tests -v
```

테스트는 평가자 간 일치와 불일치, 다수결, 누락된 출력, 잘못된 JSON과 평가 항목, 재시도 제한, UUID 중복, 실행 환경과 모델 불일치, 프롬프트의 SHA256과 결과 요약의 불일치를 검사합니다. 임시 시험 자료로 검사한 도구 동작과 실제 모델 평가 결과를 구분합니다.
